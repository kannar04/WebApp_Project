01 / From functions to data

The existing requirements already justify 22 tables. No additional app functions are needed to meet the eight-table minimum.

Added functions: none. Session tokens, password recovery, booking price snapshots and administrative history are implementation details of functions already listed in the source. This is a schema design document, not an executable migration or an implemented application.

Included in this design

  • Accounts with simultaneous Guest, Host and Admin roles; login sessions and password recovery.
  • Accommodation publishing, moderation, images, amenities, rules and availability.
  • Booking requests, approval, cancellation, price snapshots and refund calculations.
  • Verified-stay reviews, Host replies, wishlists, reports, notifications and Admin audit history.
  • Search, map coordinates and dashboard statistics derived from stored data.

Optional features left for a later phase

Use the source's simple payment-at-check-in and phone/Zalo contact options. Contact details are disclosed only after confirmation.

Online payments and refund settlement, chat, promotions, dynamic pricing, Instant Book, identity documents, recommendations, private check-in instructions and editorial posts need further design. They are not claimed as implemented here.

Language and dark-mode presentation do not require dedicated domain tables.

02 / Table catalog

PK = primary key · FK = foreign key · UQ = unique · ? = nullable. All unmarked columns are NOT NULL. Target: MySQL 8.4, InnoDB, utf8mb4. Surrogate id columns use BIGINT UNSIGNED AUTO_INCREMENT; foreign keys and the audit entity identifier use matching BIGINT UNSIGNED without auto-increment. Composite keys are assigned by the application.

MySQL conventions. Store timestamps as UTC DATETIME(6) and set every connection to time_zone = '+00:00'; DATETIME does not store a time zone. Use DECIMAL for money, JSON for snapshots and TINYINT(1) with CHECK (column IN (0,1)) for flags. Every table uses InnoDB with utf8mb4_0900_ai_ci by default. Email uses utf8mb4_0900_as_ci for case-insensitive uniqueness; token hashes use CHAR(64) CHARACTER SET ascii COLLATE ascii_bin for SHA-256 hex digests. FKs reference PK/UQ columns of the exact same type and signedness. CHECK constraints cover one row only; cross-table rules run in a transaction.

04 / Rules that protect the data

Availability & concurrency

Each listing represents one rentable unit, including a private or shared room rented as one unit. Inventory per bed or multiple identical units is outside this design.

Stay dates use [check_in, check_out), so checkout and the next check-in can share a date. MySQL prevents double approval here through a serialized transaction: START TRANSACTION; lock the listing with SELECT id FROM listings WHERE id = ? FOR UPDATE; then lock/read the booking and conflicting stays using SELECT ... FOR UPDATE. A conflict is a confirmed/completed booking on this listing with check_in < requested_check_out AND check_out > requested_check_in, excluding the current booking.

If any conflict exists, roll back. Otherwise recheck open dates, account status, capacity and allowed status transition, then confirm and append its event before COMMIT. Every booking approval, cancellation and Host calendar mutation must acquire the same listing lock first. Use locking reads for the checks to see current committed rows even under REPEATABLE READ; retry the entire transaction after deadlocks. Pending requests do not reserve inventory.

Hosts cannot close dates occupied by confirmed bookings. Missing availability rows mean unavailable. This is an application/stored-procedure transaction rule, not a MySQL CHECK constraint. MySQL locking-read reference ↗

Booking lifecycle & totals

Allowed transitions: pending → confirmed / rejected / cancelled; confirmed → completed / cancelled. All transitions append a booking event in the same transaction. Completion requires checkout to have passed.

Server validation requires check-in not in the past in the listing's time zone, checkout after check-in, guest count within capacity, an active approved listing and Guest ≠ Host.

Exactly one booking-night row is stored per stay date. total_amount = SUM(nightly_amount) + fee_amount. Snapshot the nightly rate, fixed per-stay fee, currency and cancellation policy at request time; later listing edits never change an existing booking.

Cancellation & refund amounts

Policy tiers use refundable percentages of the accommodation subtotal and a separate refundable-fee flag. Define the cutoff relative to check-in in the listing's time zone. Before cutoff, apply early_refund_pct; afterwards apply late_refund_pct.

The booking stores an immutable policy JSON snapshot containing every policy field, time zone and check-in time. Cancellation atomically records actor, reason, approved amount and booking status. Refund amount must be between zero and the booking total.

A calculated refund is an entitlement, not proof of a payment or money transfer. Payment-at-check-in needs no online transaction ledger; a payment integration must add payments and refund-settlement records.

Authorization & content

Guests access their own bookings; Hosts manage their own listings and associated bookings. Host registration grants the Host role without removing Guest. Only Admins can grant the Admin role or moderate content.

Reviews require a completed booking and its actual Guest. A unique booking ID permits one review per stay. The Host of that booking's listing alone may supply the reply. Average ratings are derived from visible reviews.

Reports require a listing or booking target. When both are supplied, the booking must belong to that listing. Role, ownership and cross-table conditions are enforced by transactions/service checks or database triggers, not ordinary CHECK constraints.

Security & retention

Store passwords using Argon2id/bcrypt and only SHA-256 hashes of high-entropy session/reset tokens. Recovery tokens expire and can be consumed once. Logout revokes the session; password reset/change and account suspension revoke existing sessions.

Use a UNIQUE index on email VARCHAR(254) COLLATE utf8mb4_0900_as_ci. Soft-delete users and listings to preserve bookings and audit trails; anonymize personal data according to the retention policy. Use ON DELETE RESTRICT on historical foreign keys. Dependent listing photos, amenity links, availability and wishlists may use ON DELETE CASCADE only when a hard delete is permitted. MySQL checks foreign keys immediately; no deferred constraints are assumed.

Keep audit rows append-only and omit passwords, tokens and private contact details from audit JSON and notification payloads. MySQL foreign-key reference ↗

Indexes & reporting

Index foreign keys, plus listings (moderation_status, is_visible, city, base_nightly_rate), bookings (guest_id, created_at), bookings (listing_id, status, check_in), notifications (user_id, read_at), and reports (status, created_at). Use a text-search index for listing titles/descriptions; spatial indexing can be added for map bounds.

PK/UQ constraints already index role membership, amenity links, availability dates and wishlist pairs. Derive Host/Guest totals from roles and completed-stay revenue from completed booking snapshots. Label this revenue as booked revenue; actual collected revenue requires a payment ledger.
